About this mockup (design exploration for CARD-0043, not the real viewer)
  • Highlighted text and left bars mark existing threads. Blue is a comment, amber is a change request. Dotted underlines are resolved or obsolete threads.
  • Hover a highlight or a card to see which belongs to which. Click either to open the thread; the card lines up with the text and the others move aside. Press Escape to close.
  • Click any word to select it, then use the floating toolbar or the "Comment on selection" pill in the margin. Expand grows the selection to sentence, paragraph and section.
  • Inside an open thread you can reply, and mark it resolved, obsolete or open again. Untick "Show resolved and obsolete" to keep only open threads in the rail.
  • Make the reading pane narrower than about 900px: the rail folds away and threads open inline under their block instead.

2. Terminology

  • Package: one ZIP file conforming to §3. The working file extension is .mdpkg (registration is open, §11.1).
  • Current view: the plain ZIP entries that are the Git working tree of the commit named by the manifest's current field. Every Markdown document, and the override ledger, is here.
  • Container-level entries: the entries under .mdpkg/ that are not tracked in Git, because they name commit identities that cannot appear inside the tree they describe: .mdpkg/manifest.json, .mdpkg/history.json, .mdpkg/history/bindings.json, .mdpkg/history/ranges/*.json, .mdpkg/history/patches/*.patch.
  • Namespace: the lowercase UUID identifying a package lineage. All addressing roots are derived within it.
  • Entity: a document, a document's permanent preamble, or a heading section. Each has a locator (§6.2) and, at any snapshot, a scoped digest (§6.1).
  • Root: the 64-hex SHA-256 that is an entity's stable identity: its default root unless the ledger says otherwise.
  • Canonical JSON: UTF-8, object keys sorted bytewise, compact separators (, and :), no ASCII-escaping of non-ASCII characters, exactly one trailing LF. Every JSON file this format defines is written this way, with one exception: the manifest writes its mdpkg key first (§4).

4. The manifest

.mdpkg/manifest.json is canonical JSON with one deliberate exception: the mdpkg key is written first so it lands at byte 50 of the file. All other keys are in sorted order. It MUST be O(1) in package size: a field earns its place only if a reader needs it before it can do anything else, it must be readable without a decoder, and it does not grow with the package.

{"mdpkg":"markdown-package/1",

One further object is defined and is present only in a review package (§6.8), where it is genuinely read before a reader can do anything else: it is how a reader tells a review package from an ordinary one and decides whether it must go and find the reviewed original.

 "review":{"detail":".mdpkg/review/comments.json",
           "of":{"current":"sha1-…","dispatch":"…","namespace":"c1b2d3e4-…","packageBytes":251778,"packageDigest":"sha256-…"},
           "shape":"delta"}
FieldTypeMeaning
review.of.namespace, review.of.currentUUID, qualified object IDThe correlation key: the exact lineage state this package reviews. Both REQUIRED. A reader matches on the pair and on nothing else, exactly as §6.4 rejects a reference from a foreign namespace before resolving anything (D-25).
review.of.packageDigest, review.of.packageBytesstring, integerCorroborating evidence, OPTIONAL and RECOMMENDED: the SHA-256 and length of the file the reviewer held. A match means the reviewer held those exact bytes; current matching while the digest does not means the same lineage state was re-emitted or repacked, which is a fact worth reporting and is not an error; if current does not match, the digest is irrelevant. Never identity (D-25).
review.of.dispatchstringOPTIONAL transport metadata echoed back from the sender, stored and never interpreted. A producer that fixes commit dates can emit two byte-identical packages at different times, and no content-derived identifier can tell them apart; which send a review answers is transport knowledge, not package identity (D-26).
review.shapedelta or bundleddelta carries the review alone in the reviewer's own fresh namespace; bundled carries the reviewed package too and continues its lineage (D-24, §6.8).
review.detailentry nameThe tracked review document, §6.8. Normally .mdpkg/review/comments.json; the initial .NET Reader/Reviews implementation supports that exact path and reports other paths as an unsupported capability.

The object is O(1) with a fixed key set, and it is the only manifest field whose absence is itself the answer to a question: a package without review is not a review package.

Fields deliberately absent, with their measured cost on the npm / Rust corpora: a codec declaration (+42 / +42 bytes; the central directory already holds every entry's method), a document index (+3,527 / +22,228; the central directory is the index), per-document digests (+9,086 / +65,776; the tip tree already binds them and ZIP CRCs catch accidental corruption), entry counts or offsets (EOCD), and a package self-hash (a file cannot contain its own digest).

A validator MUST reject a package whose manifest disagrees with the archive: current not equal to the branch target, overrides naming an entry that is absent or absent when the tree contains the ledger, or a transform list inconsistent with history.json.

Two further obligations apply to a package carrying review, and both are checkable from what a validator already holds:

  • A bundled review package's namespace MUST equal review.of.namespace, and its tip commit MUST change only paths under .mdpkg/review/: no document edits and no ledger edits. A validator checks the whole claim by diffing the tip tree against its parent, whose commit MUST be review.of.current. This is what makes it safe for a reviewer to be briefly a producer in the reviewed lineage without confirmation authority under §6.3: no addressing exception is created, every root stays valid, and the ledger is copied with the tree.
  • A delta review package's namespace MUST differ from review.of.namespace. A delta review is the reviewer's own one-commit lineage over its own review document; each exported delta is a snapshot even when the authoring tool retains a private edit history; the roots and digests inside it belong to the reviewed namespace and are read there (§6.8), and collapsing the two namespaces would make every thread a self-reference.

A validator MUST also check the producer requirements that are otherwise stated with no addressee: entry-name uniqueness under NFC plus simple case folding (§3.6, D-16), the reserved-prefix rule (§3.6), LF-only content in every entry outside .git/ (§3.6, D-17), and internal file attributes of 0 on every central-directory record (§3.5, D-19). All four are cheap from what a validator already holds, and each describes real damage a reader cannot detect for itself. A reader is not required to make these checks; §3.7's two tiers are about typing and recovery, not content conformance, and a package that fails any of them may still type as conforming at offset 0.
